# Phase 6 — CUDA feasibility measurements

**Date:** 2026-08-26 / 2026-08-27
**Status:** feasibility study. **No CUDA backend exists, and no dependency was
added.** This report is the evidence a dependency proposal would have to cite.

---

## 1. Why this exists

CLAUDE.md §1 makes adding a dependency a core-level decision requiring written
justification and explicit approval. Rather than propose `cudarc`/`cust` on
expectation, a standalone CUDA C prototype was written to establish what a CUDA
path actually does on this hardware — with no Rust binding, no vendored crate,
and no change to library code.

The prototype answers three questions:

1. does a CUDA kernel with the same semantics as `shaders/spmm.wgsl` reproduce
   the CPU oracle;
2. does the feature-dimension-dependent workgroup preference survive a
   completely different compiler and runtime;
3. does the large-transfer readback cliff recorded in
   `2026-08-25-published-baseline-benchmark.md` Appendix A.5 appear under CUDA on
   the same hardware.

## 3. Level 1 — Established

Findings reproduced directly, with the discriminating check stated.

### 3.1 The workload generator port is exact

A C reimplementation could silently produce a *different* matrix, which would
invalidate every comparison. It is therefore checked against known Rust outputs
rather than trusted:

| spec | Rust nnz (from the published sweep) | C port nnz | match |
|---|---:|---:|:-:|
| 200 000 rows, deg 8, uniform | 1 599 965 | **1 599 965** | ✓ |
| 50 000 rows, deg 8, uniform | 399 970 | **399 970** | ✓ |

The RNG consumption order is load-bearing — degrees, then columns, then one
weight per *surviving* column after sort+dedup. Drawing weights before dedup
desynchronises the stream and yields a different matrix with the same nnz
target. The exact match confirms the order was preserved.

### 3.2 CUDA output agrees with the CPU oracle

| workload | fd | elements | worst relative error | failures |
|---|---:|---:|---:|---:|
| 50 000 rows, deg 8, uniform | 8 | 400 000 | 3.068 × 10⁻⁷ | 0 |
| 50 000 rows, deg 8, uniform | 32 | 1 600 000 | 2.975 × 10⁻⁷ | 0 |
| 20 000 rows, deg 32, **irregular** | 32 | 640 000 | 3.383 × 10⁻⁷ | 0 |

Worst case **3.383 × 10⁻⁷** — single-ULP for f32. Consistent with the kernel
contracting `acc + v·x` into an FMA, rounding once where the CPU rounds twice.
That is a per-term rounding difference, not a reordering, and bit-exactness was
never claimed.

### 3.3 The fd-dependent workgroup preference reproduces under CUDA

200 000 rows, degree 8, uniform. Median kernel time:

| block (x=feature, y=row) | fd 8 | fd 32 |
|---|---:|---:|
| **8 × 8** | **294.5 µs** | 925.7 µs |
| 16 × 8 | 361.0 µs | **926.2 µs** |
| 16 × 16 | 364.5 µs | 937.7 µs |

* At **fd 8**, 8 × 8 is **18.5 % faster** than 16 × 8 — well outside the 3 %
  floor used throughout this project.
* At **fd 32**, 8 × 8 and 16 × 8 are within **0.05 %** (a tie), and 16 × 16 is
  1.3 % slower — the worst of the three.

This is the same preference `spmm_workgroup_for` encodes from wgpu measurements
(`fd < 16 → 8×8`, else `16×8`; 16×16 never selected). It now reproduces on
**different compiler machinery (nvcc/PTX rather than naga/SPIR-V) and a different
runtime (CUDA rather than Vulkan)**.

**What this supports:** the occupancy explanation — when `feature_dim < block.x`,
surplus lanes are masked off and the block runs at a fraction of its occupancy.

**What this argues against:** the preference being an artifact of WGSL, naga's
code generation, or the Vulkan driver's shader compiler.

It does **not** establish that the specific constants generalise to other GPUs;
that is a separate claim requiring other hardware.

### 3.4 CUDA `cudaMemcpy` shows no large-transfer cliff on this hardware

Device-to-host, 200 000-row family, fd 128, swept densely through the region
where the wgpu path collapses:

| transfer size | median | throughput |
|---:|---:|---:|
| 32 MB | 3 089.7 µs | 10.86 GB/s |
| 48 MB | 4 596.9 µs | 10.95 GB/s |
| 64 MB | 6 090.1 µs | 11.02 GB/s |
| 80 MB | 7 592.1 µs | 11.05 GB/s |
| 96 MB | 9 098.4 µs | 11.06 GB/s |
| 112 MB | 10 623.1 µs | 11.06 GB/s |
| 128 MB | 12 023.2 µs | 11.16 GB/s |

Also 6 MB at 9.96 GB/s and 24 MB at 10.77 GB/s.

Throughput is **flat to slightly rising across 6 → 128 MB**. There is no
discontinuity anywhere in the swept range.

## 4. Level 2 — Strongly isolated, stated with care

### 4.1 What was previously recorded

`2026-08-25-published-baseline-benchmark.md` Appendix A.5 recorded, on this same
amaterasu hardware through wgpu:

> ~41 MB at ~11 GB/s but ~102 MB at ~1.1 GB/s — a **~10× collapse between
> roughly 41 MB and 51 MB** … **Observed, not explained.**

That text stands unchanged. This section is an addition to it, not a rewrite.

### 4.2 What the CUDA measurement adds

CUDA `cudaMemcpy` on the **same GPU, same driver, same host, same transfer
sizes** sustains 10.86–11.16 GB/s through 32–128 MB with no discontinuity
(§3.4).

**Therefore: PCIe link bandwidth and the GPU DMA engine alone do not explain the
cliff.** If either were the limiting mechanism, CUDA would exhibit it too, and it
does not.

### 4.3 What this does and does not license saying

**Supported:** the cliff lies in the **tested wgpu readback path** — that is,
`WgpuBackend::read_tensor` as implemented here — or in that path's interaction
with the backend/driver mapping machinery on this platform.

**Not supported, and not claimed:**

* that wgpu is universally defective. One readback implementation, on one
  backend, one driver, one OS, one GPU, at one set of sizes was measured.
* that the mechanism is known. Staging-buffer allocation strategy, buffer
  mapping, synchronisation between submit and map completion, transfer chunking,
  or something else entirely — **none of these was isolated.** Naming one would
  be a guess presented as a finding.
* that our own `read_tensor` is necessarily at fault rather than the layer
  beneath it. The measurement cannot separate the two.

The honest summary: *the cliff is not in the hardware transfer path; it is
somewhere in the software readback path, and which part is unknown.*

## 5. Level 3 — Not comparable, and deliberately not computed

The temptation is to divide CUDA's kernel time by wgpu's resident time and
publish a speedup. That number would be wrong.

| measurement | value | what the boundary includes |
|---|---:|---|
| CUDA, 200 000 rows, deg 8, fd 32 | 920.9 µs | **kernel execution only**, between two `cudaEvent`s |
| wgpu, same workload, amaterasu | 1 416.2 µs | session creation + encode + submit + device wait + kernel |

**No CUDA-vs-wgpu kernel speedup is calculated or published from these two
numbers.** They measure different spans. The difference — roughly 495 µs —
plausibly contains submission and synchronisation overhead that the CUDA figure
excludes by construction, but the split was not measured, so even that is a
hypothesis.

**What a valid comparison requires:** wgpu timestamp queries written around the
compute pass (`DeviceCapabilities` already reports `timestamp_query` support and
`timestamp_period_ns`), giving pure shader execution time, compared against
`cudaEvent` boundaries placed equivalently. Until both sides measure the same
span, the comparison is not available.

## 6. Level 4 — Hypotheses and next discriminating experiments

Ordered by what each would settle. None has been run.

1. **wgpu timestamp queries around the compute pass.** Settles §5: gives pure
   shader time on the wgpu side, making a like-for-like kernel comparison
   possible for the first time.
2. **Decompose readback into its four stages** — GPU-side copy to the staging
   buffer, submission and wait, map completion, host `memcpy` out of the mapped
   range. This is the experiment that would name the mechanism in §4, converting
   "somewhere in the software path" into a specific stage.
3. **Sweep densely across 32–128 MiB on the wgpu side.** CUDA is now swept at
   16 MB granularity (§3.4); the wgpu side has only two points bracketing the
   collapse. A matching sweep would locate the transition precisely and show
   whether it is a step or a knee.
4. **Staging-buffer reuse versus fresh allocation per readback.** If reuse
   removes the cliff, allocation is implicated; if not, it is excluded.
5. **Chunked versus single-buffer readback.** If transferring 128 MB as 8 × 16 MB
   restores full throughput, the limit is per-transfer rather than aggregate.
6. **Repeat on Blackwell (RTX 5080) and Turing (RTX 2070 SUPER).** Appendix A.5
   showed the laptop scaling smoothly at ~2.4 GB/s where amaterasu collapses, so
   the interaction is platform-dependent and both need the same treatment.

## 7. Threats to validity

* **Single host, single GPU, single driver.** Every CUDA number here is one
  Turing part on one Linux driver. Nothing about other architectures follows.
* **The workload generator is a reimplementation.** Verified by nnz equality at
  two configurations (§3.1), which is strong but not exhaustive: a divergence
  that preserved nnz while changing values would pass this check. The correctness
  comparison in §3.2 is against a CPU oracle *within the same program*, so a
  shared misunderstanding of the CSR semantics would not be caught by it — only
  by the nnz check and by the kernel matching `spmm.wgsl`'s documented
  semantics.
* **`-arch=native` bakes in the host GPU's architecture.** Timings are not
  portable to a different compute capability without recompilation.
* **Kernel timing excludes launch overhead**, by design. That makes it the right
  number for kernel comparison and the wrong number for end-to-end cost.
* **The CPU oracle is single-threaded and unoptimised** in the prototype. It is
  used only for correctness, never for a performance claim.
* **wgpu comparison figures come from a different process and session** than the
  CUDA ones, though on the same host and hardware. Ambient conditions were quiet
  in both cases (load 0.37–0.56, GPU idle), but they were not interleaved.
* **The readback measurement uses pageable host memory.** Pinned memory would
  likely be faster; this was not varied, so the CUDA figures are a floor rather
  than a peak for that path.

## 8. Dependency position

**CUDA remains an optional, experimental, native-backend *candidate*.** It is:

* **not a required dependency** — nothing in the workspace needs it, and the
  prototype is standalone C compiled by `nvcc`, outside cargo;
* **not a replacement for the WGPU backend** — wgpu is portable across Vulkan
  and DX12 and runs on the laptop, which has no CUDA toolkit installed at all;
* **not proposed for adoption in this report.** No `cudarc`, `cust`, or
  `rustacuda` dependency is requested, and `Cargo.lock` is untouched.

What the measurements support is narrower and worth stating exactly: a CUDA path
is **numerically viable** (§3.2) and **reproduces the workgroup behaviour**
(§3.3), and its transfer path does not exhibit the cliff (§3.4). Whether that
justifies a second GPU backend depends on the §6 experiments — particularly (1),
which is the only way to compare kernels honestly.

Adoption would require, per CLAUDE.md §1: a written justification, the
transitive dependency cost measured against the shared `vendor/` tree, and
explicit approval. None of that is sought here.

## 9. Architecture note — how a CUDA backend would attach

Sketch only; nothing implemented.

The existing typed model already has the right seams, and a CUDA backend would
attach behind them rather than beside them:

* **Shared vocabulary stays in `hymeko_core`.** `TensorShape`, `SparseCsrShape`,
  `ComputeError` and `try_u32` are backend-independent by construction, and
  `BackendKind` already has a variant slot. A CUDA backend would depend on
  `hymeko_core` only — the same rule that keeps `hymeko_wgpu` free of
  `hymeko_hnn`.
* **The builder/prepared-operation split ports directly.** `prepare()` performs
  every fallible check and `encode()` is infallible; on CUDA, `prepare()` would
  resolve the module and grid configuration, and `encode()` would record into a
  stream instead of a `CommandEncoder`.
* **Provenance must not weaken.** `TensorOperand` is sealed via a `pub(crate)`
  supertrait, and no public API returns a raw `&GpuTensor` for a pooled lease. A
  CUDA backend must preserve both: its device pointers stay behind an equivalent
  sealed accessor, and a pooled CUDA tensor must be `Tracked` so it can only be
  encoded into a tracked stream. **No raw arena buffer may be exposed** — that
  was closed once already (`PHASE-5-CORRECTIVE`) and must not be reopened for a
  second backend's convenience.
* **Completion tracking generalises; the encoder shape does not.**
  `SubmissionEpoch` and the monotone watermark are expressed in terms of
  submissions completing, and CUDA streams with events fit that model. But the
  watermark's validity rests on **in-order completion within one queue**
  (`completion.rs`); CUDA streams are independent timelines, so multiple streams
  would need one watermark per stream, exactly as the multi-queue case is already
  documented as unsupported. `TrackedSession` is encoder-shaped and would need a
  stream-shaped sibling rather than a rename.
* **The arena is reusable in structure.** `TensorArena` deals in byte sizes,
  usage flags and epochs, none of which are wgpu-specific. `AllocationKey`'s
  usage field would become CUDA's allocation kind.

The layering rule that matters: a second backend goes **beside `hymeko_wgpu`,
both depending on `hymeko_core`** — never beneath it, and never with the CPU
path depending on either.

## 10. Reproduction

```sh
# On a host with a CUDA toolkit. No absolute paths; nvcc comes from
# $NVCC, $CUDA_HOME/bin/nvcc, or PATH.
cd tools/cuda_prototype
./build.sh                      # or: CUDA_HOME=/opt/cuda ./build.sh
                                # or: ARCH=sm_75 ./build.sh   (cross-compile)

./spmm_prototype --check-nnz                                   # §3.1
./spmm_prototype --rows 50000 --deg 8 --fd 32 --verify         # §3.2
./spmm_prototype --rows 20000 --deg 32 --fd 32 --irregular --verify
./spmm_prototype --rows 200000 --deg 8 --fd 8 --bx 8  --by 8  --bench   # §3.3
./spmm_prototype --rows 200000 --deg 8 --fd 8 --bx 16 --by 8  --bench
./spmm_prototype --rows 200000 --deg 8 --fd 128 --bench                 # §3.4
```

The compiled binary is **not** committed (`tools/cuda_prototype/.gitignore`).
The prototype source is committed because §3 cannot be reproduced without it.
