## 0.5 User decisions recorded (2026-08-28)

M0.5 surfaced several questions that were underspecified at the language level. They have been decided. These are **language and architecture contracts**, not implementation notes, and they propagate to `docs/unified-ir-architecture.md`, `docs/unified-ir-migration.md` and `docs/unified-ir-dynamic-test-plan.md`.

| # | Decision | What it settles | Consequence |
|---|---|---|---|
| **U1** | **Arc order and reference-slot order are semantic and must be preserved.** | The C4 ambiguity (§3). | Resolves **H2 → H0** under an explicit contract. The hash's existing behaviour is now the *specified* behaviour, not an accident. Any rewrite that reorders arcs or slots changes program identity and is a breaking change. |
| **U2** | **The target canonical hierarchy is `parent`/`children` in `Ir`. The path `Index` becomes a derived, versioned view. A coherence validator is required during migration.** | Which of the two hierarchies is authoritative (§2). | **Inverts today's behaviour** — the canonical hash currently reads `Index` path prefixes and ignores `DeclNode.parent` entirely (proven in §3). Migration must flip the authority and prove the two agree while both exist. |
| **U3** | **Duplicate incidences are permitted as distinct entities with distinct `HyperArcId`s. Multiplicity is semantic. Removal is by incidence ID.** | The duplicate-incidence policy left open in the test plan. | Removal must never be by `(sign, target)` matching — that would delete an arbitrary member of a multiset. |
| **U4** | **General `ValueR::Num` preserves all IEEE-754 bit patterns. Algebraic incidence/edge weights must be finite. Negative zero is permitted and bit-preserved. Canonical ordering uses `total_cmp`, never `partial_cmp`.** | The NaN/Inf policy left open. | Two distinct rules: the *value* type is bit-faithful; the *algebraic weight* position is validated finite. `-0.0` and `+0.0` are distinguishable, so ordering and digests must not normalise them away. |
| **U5** | **No language-level declaration-depth limit now. Recursive traversal must become iterative before the canonical-hierarchy migration. A future configurable resource limit is separate from language semantics.** | The D3 question (§5). | Verdict stays **D1**. The recursion is a defect to fix, not a limit to codify — and it must be fixed *before* U2, since U2 makes the intrusive hierarchy authoritative and therefore load-bearing for traversal. |
| **U6** | **Two identities are maintained: an O(delta), history-sensitive commit-chain digest on every commit; and a history-independent canonical semantic hash for checkpoint, audit and convergence. Full `canonical_program_hash` is not allowed on the 100 Hz commit hot path.** | The M4.1 open question, which §6's measurement made urgent. | Directly answers the 10.74 ms measurement: the hot path never runs the expensive whole-graph hash. The two identities answer different questions and neither substitutes for the other. |

**U4 has an immediate consequence for existing code.** `total_cmp` ordering means any sort or comparison over `ValueR::Num` must be audited: `partial_cmp` on a `NaN` returns `None`, and a sort relying on it is not merely wrong but *unstable*. No such audit was performed in M0.5; it is recorded as migration work.

## 2. Part B — semantic oracle, and the ordering question

`tests/unified_ir_m05/oracle.rs` derives meaning by walking `Ir` and `Index` directly and emitting a normalised textual form. **It never calls `canonical_program_hash`** — otherwise "equivalent histories hash identically" would be a tautology.

The oracle keys everything on **paths**, never on dense IDs, and sorts declarations, tags and bases. It deliberately offers *two* readings of positional order.

### What is semantic and what is representational

| Ordering | Status | Evidence |
|---|---|---|
| Dense `DeclId`/`NodeId`/`EdgeId` assignment | **representational** | hash keys on `PathKey`; `verts`/`children`/`roots` sorted before use |
| Sibling order | **representational** | `compute_subtree_hashes_with_kinds` sorts child hashes (`ch.sort()`) |
| `Ir.nodes` / `Ir.edges` insertion order | **representational** | never read positionally |
| **Arc order within an edge** | **SEMANTIC — by the hash** | `canonical_incidence_bytes` writes `ai as u16` and sorts on it |
| **Reference slot within an arc** | **SEMANTIC — by the hash** | same function writes `slot as u16` |
| `DeclNode.parent`/`first_child`/`next_sibling` | **NOT READ AT ALL** | skeleton forest built from `Index` path prefixes |

### The ambiguity — identified, then decided

M0.5 surfaced two underspecified points. Both have since been settled by explicit user decision (§0.5); the findings and the decisions are recorded separately so the evidence remains legible.

1. **Arc order and reference-slot order.** *Found:* the hash treats both as meaning-bearing — it writes `ai as u16` and `slot as u16` into the incidence bytes. Nothing documented that as a language choice. **C4 demonstrates it empirically** (§3).
   → **Decided (U1): they are semantic and must be preserved.** The hash's behaviour is now the specified contract. The observed behaviour did not change; its *status* did — from accident to specification.

2. **Which hierarchy is authoritative.** *Found:* the intrusive links are invisible to the hash. `DeclNode.parent`/`first_child`/`next_sibling` are never read; the skeleton forest is built from `Index` path prefixes. An `Ir` whose parent links contradict its paths hashes as though only the paths existed — two structures, one silently ignored. **Proven by a dedicated test** (§3).
   → **Decided (U2): the target canonical hierarchy is `parent`/`children` in `Ir`; the path `Index` becomes a derived versioned view.** This **inverts** today's behaviour, so the migration must flip the authority and, while both exist, run a **coherence validator** proving they agree. Until that flip lands, the *measured* behaviour in this report — path-authoritative — remains what the code does.

The gap between (2) as found and (2) as decided is the largest single piece of work M0.5 hands to the migration.

### Verdict

**H0 for every layout and build-order case**, and it is a strong H0: in each of C1, C2, C3, C5, C6 and C10 the dense IDs genuinely differed (`dense_ids_differ=true`) and the hash was still identical. The canonical hash is invariant to declaration order, sibling permutation, node/edge interleaving, dense-ID assignment, churn residue and reconstruction order.

**C4 is now a conformance test, not an open question.** Two IRs with an identical *bag* of signed references in one arc, differing only in slot order, hash differently. Under **U1** that is the *required* behaviour: order is semantic, so the two IRs are not equivalent and must not share a hash. C4 asserts it and will fail if a future change makes the hash order-insensitive — which under U1 would be a regression, not an improvement.

**No H1.** No counterexample was found where the oracle says equivalent and the hash disagrees. Consequently:

> **The passing invariance tests are committed as permanent gates.** No ignored counterexample fixture was needed.

### Which M3 assumption this validates

M3 moves the arenas to generational keys, changing dense-ID assignment wholesale. C5 and C6 are the direct evidence that this **cannot** perturb the canonical hash. The migration's ordering assumption survives — measured, not assumed.

Two caveats it does *not* clear:
- **Arc/slot order must be preserved by any future rewrite** — C4 shows the hash is sensitive to it, so a "harmless" reordering during M3 would change program identity.
- The 580-entry order-column triage (`unified-ir-id-inventory.md` §4) is still required: this tests the *hash*, not every consumer that iterates in ID order.

## 5. Part E — declaration-depth audit: **D1, with a wide margin**

### Real corpus — structure first

| Metric | Value |
|---|---|
| Fixtures found | 110 `.hymeko` |
| Lowered successfully | **96** (14 failed — import-only/library files) |
| Total declarations | **6 840** |
| Depth: median / p95 / p99 / **max** | 3 / 5 / 5 / **5** |
| Max branching factor | 15 |
| Deepest path | `meta_kinematics.kinematics.controllers.forward_velocity_controller.type` |

### Recursion and the stack boundary

`canonical_hash::compute_subtree_hashes_with_kinds` contains an inner **`fn rec(...)`** that descends one stack frame per hierarchy level. It is memoised, but memoisation bounds *repeat work*, not *stack depth*.

Measured by child process (`examples/ir_depth_probe`), bisected:

| Build | Deepest OK | Shallowest FAIL |
|---|---:|---:|
| release (1 MB main stack) | **458** | 465 |
| debug (test-thread stack) | **215** | 223 |

≈2.2 KB of stack per level. **The boundary is build-profile dependent**, which matters: a limit validated in release does not hold in debug.

| Path | Recursive? |
|---|---|
| `compute_subtree_hashes_with_kinds` | **recursive** — the limiting path |
| Intrusive parent walk | iterative (loop) |
| `Ir` drop | iterative — flat `Vec`s, no linked structure |
| `canonical_incidence_bytes` | iterative |
| Semantic oracle | iterative |

**Malformed cycles:** a `next_sibling`/`parent` cycle in the intrusive links cannot cause infinite traversal *in the hash*, because the hash never reads those fields. The skeleton forest is derived from path prefixes, which cannot be cyclic (a strict prefix is strictly shorter). A cycle in the intrusive links is therefore currently **undetected but also unreached** — a latent hazard for M3, when those links become authoritative.

**No maximum depth is enforced anywhere.**

### Verdict: **D1**, not D2 or D3

- **D1 (recursion/stack risk): confirmed.** A real recursion with a real, measured limit.
- **Not D2.** Observed depth is 5 against a boundary of 215–458 — a margin of **43–92×**. The Merkle fold's O(changed × depth) term is *cheap* on real data: depth 5 means an incremental identity update touches ~5 ancestor digests.
- **D3 declined — decided (U5).** No language-level depth limit is imposed, now or as a deferred intention. The decision names the *recursion* as the defect rather than the depth: **recursive traversal must become iterative before the canonical-hierarchy migration (U2)**, because U2 makes the intrusive hierarchy authoritative and therefore load-bearing for traversal. Any future depth cap is a **configurable resource limit, separate from language semantics** — it may bound what a given deployment accepts, but it may not change what a program *means*.

  This ordering matters: U2 without U5 would move the authoritative hierarchy onto a structure whose traversal still overflows at 215 levels. U5 before U2 is a hard sequencing constraint, not a preference.

**The irony is on record:** the M0.5 depth test itself included depth 1000 in-process, overflowed, and aborted the whole test binary with `STATUS_STACK_OVERFLOW`, taking 150+ unrelated tests with it. In-process depths are now capped at 100 and the deep cases run as a child process. This is exactly the failure the brief anticipated.

### Merkle cost model, with real numbers

`changed × ancestor_depth` at depth 5 ⇒ ~5 digest recomputations per changed declaration. Negligible. **The fold's depth term is not the problem** — §6 shows what is.

### The result that changes a design conclusion

> **`canonical_program_hash` costs 10.74 ms at 15 000 declarations.** The 100 Hz non-topology commit budget is **10 ms**. Full-state canonical hashing therefore **already exceeds the entire budget at a graph 7× smaller than the 10⁵-declaration target.**

Phase 0's contaminated appendix measured a *flat BLAKE3 sweep* (0.89 ms at 40 001 elements) and was explicit that it was a lower bound on real canonical-identity cost. It was: the real hash is roughly **12× more expensive per declaration** than the proxy implied.

Three consequences:

1. **Incremental identity is not a scale-up concern — it is already out of budget.** The architecture's requirement is confirmed and its urgency raised.
2. **The depth term is not the bottleneck.** Depth is 5; the fold's O(changed × depth) is trivial. The expensive stages are the **whole-graph** ones: `build_did_to_path`, `build_skeleton_forest`, the Prüfer encoding and the incidence sort. A Merkle fold over subtree digests **does not by itself fix this**.

   → **Decided (U6): maintain two identities.** An **O(delta), history-sensitive commit-chain digest** runs on every commit; a **history-independent canonical semantic hash** is reserved for checkpoint, audit and convergence. **Full `canonical_program_hash` is not allowed on the 100 Hz commit hot path.**

   This takes the second of the two options M0.5 identified rather than trying to make the whole-graph stages incremental. The reasoning it rests on is that the two identities answer genuinely different questions: the commit-chain digest says *"is this the same sequence of changes I already applied"* — which is what replay detection and conflict detection need, and which is inherently history-sensitive; the canonical hash says *"do two independently-built graphs mean the same thing"* — which is what convergence and audit need, and which must be history-**in**sensitive. Neither substitutes for the other, and the C1/C5/C6 results are what make the second one trustworthy: they show the canonical hash really is history-independent across dense-ID and build-order differences.
3. **JSON is not a candidate transport.** Deserialising 15 000 declarations costs 9.06 ms — the whole commit budget, again.

Secondary: `ir_clone` at 1.25 ms/15 000 declarations makes a clone-based transactional overlay viable at 10 Hz topology (1.2% of budget) but **not** at 100 Hz (12.5%). Lookup at 2–5 Gelem/s sets a demanding baseline for M2d's derived index.

## 7. Parts G, H, I

Delivered as `docs/unified-ir-dynamic-test-plan.md`: reference-model constraints, entity lifecycle, referential integrity, transactions, the 14 mutation operations with their per-operation matrices, hierarchy, incidences, derived views, distributed/replay, model-based mutation properties P1–P8 with shrinking requirements, and the future performance matrix.

Three points the phase surfaced; all three are now decided:

- **`UpdateIncidenceSign` is classified topology, not weights** — sign is three-valued and participates in incidence structure; classifying it as a weight update would let a 100 Hz path skip a structural rebuild. *(Analysis, unchanged.)*
- **Duplicate incidences — decided (U3):** permitted as **distinct entities with distinct `HyperArcId`s**; multiplicity is semantic; **removal is by incidence ID**. This is consistent with what the hash already does — it writes the slot index and therefore already distinguishes duplicates. The binding consequence is on the delta vocabulary: `RemoveIncidence` must take an **ID**, never a `(sign, target)` pattern, which would delete an arbitrary member of a multiset.
- **NaN/Inf — decided (U4):** general `ValueR::Num` **preserves all IEEE-754 bit patterns**; **algebraic incidence/edge weights must be finite** (validated); **negative zero is permitted and bit-preserved**; canonical ordering uses **`total_cmp`, never `partial_cmp`**.

  Note this is *not* the blanket rejection M0.5 recommended. The decision separates two roles the earlier recommendation conflated: `ValueR::Num` as a general value carrier stays bit-faithful (so a NaN payload survives a round trip), while the *algebraic weight position* is constrained to finite values. `total_cmp` then gives a total order over all bit patterns including `-0.0` and NaN, which is what makes ordering deterministic without normalising anything away.
